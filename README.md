# IBDS

웹 애플리케이션의 SQL 인젝션(SQLi)과 크로스사이트 스크립팅(XSS) 취약 가능성을 자동으로 점검하는 동적 점검 도구입니다.

> **주의**: 반드시 본인이 소유·관리하는 서버나 벤치마크 테스트 전용으로 만들어진 웹만 점검할 것.
> 허가받지 않은 사이트에 해당 도구를 사용시, 법적 책임이 따를 수 있습니다.

## 1. 프로젝트 구성

### 동작 흐름

수집 → 정규화 → 점검 지점 분리 → (XSS) 사전 확인 → 변형 요청 생성 → 전송 → 판정 → 결과 저장·집계 → 화면·보고서

- 수집: ZAP이 대상 사이트를 크롤링하고 요청 및 응답 기록을 저장. 로그아웃·삭제성 주소는 제외 목록으로 미리 걸러냄
- 정규화: ZAP 기록을 요청 대상으로 바꾸고, 보안 토큰이나 파괴적 동작이 있는 요청은 점검에서 제외
- 점검 지점 분리: 파라미터 하나하나를 점검 지점으로 분리
- 사전 확인 (XSS 반사형): 표식 문자열로 반사 여부와 HTML 문맥을 확인해 불필요한 공격 요청을 미리 줄임
- 변형 요청 생성: 지점마다 기준 요청 1개와 공격 요청 여러 개를 한 묶음으로 구성
- 전송: 모든 요청을 ZAP을 거쳐 전송. 안전한 메서드만 재시도
- 판정: 기준 응답과 비교. XSS는 헤드리스 브라우저로 실제 실행까지 확인
- 보고: 웹 화면에서 결과 조회, PDF 보고서 내려받기

### 판정값

- 취약 가능성 높음: 명확하고 반복 가능한 공격 성공 근거 확인
- 취약 신호 관찰: 신호는 있으나 실행 또는 재현성 부족
- 공격 근거 미확인: 점검을 끝냈고 근거를 찾지 못함
- 판단 보류: 점검을 끝내지 못해 결론을 낼 수 없음
- 일부 요청이 실패하거나 실행되지 않았다면, 나머지가 근거 없음이어도 "판단 보류"로 처리

### 디렉터리 구성

- `src/collector/`: ZAP 연동과 수집
- `src/scan/normalize/`: ZAP 기록 → 요청 대상 → 점검 제외 판단
- `src/scan/mutation/`: 점검 지점, 사전 확인, 묶음 및 변형 요청 생성
- `src/scan/match/`: 공격 규칙 선택, 값 치환, 실행 토큰
- `src/scan/requester/`: 전송과 쿠키 관리
- `src/attack_requests/`: SQLi, XSS 공격 규칙
- `src/analyzer/`: 판정 로직
- `src/metrics.py`: 검사 지점 집계와 채점
- `src/web/`: 웹 화면과 PDF 보고서
- `config/`: 점검 대상·ZAP 접속 설정

### 판정 기준 요약

- SQLi
    - 기준 요청 전송이 실패하면 비교가 불가능하므로 판단 보류
    - 오류 기반: 공격 응답에만 DB 오류 문구가 나타나면 관찰, 정보 추출 표식까지 나타나면 높음. 기준 응답에도 오류 문구가 있으면 근거 미확인
    - 시간 기반: 지연 요청이 기준보다 충분히 느린 경우가 2회 이상 재현되면 높음, 1회면 관찰
    - 불리언: 참 조건 응답은 기준과 비슷하고 거짓 조건 응답은 달라야 함. 이런 짝이 반복 재현되면 높음
    - 불리언 비교 전 반사값과 동적 영역을 제거하고, 기준 응답 유사도와 대조 요청의 잡음을 반영하는 단일 판정 규칙 적용
- XSS
    - 1차: 응답 본문에 공격 값이 반사되는지 확인
    - 2차: 헤드리스 브라우저로 실제 실행 확인. 이번 시도의 실행 토큰이 담긴 경고창만 "실행됨"으로 인정
    - 실행 확인 → 높음 / 반사만 확인 → 관찰 / 반사 없음 → 근거 미확인 / 브라우저 확인 실패 → 판단 보류
    - 저장형: 표식을 저장해 재조회 주소에서 나타나는지 먼저 확인하고, 공격 전후 재조회 본문의 차이만 판정에 사용

## 2. 설치 방법

- 준비물: Windows + PowerShell, Python 3.11, Docker (ZAP 컨테이너 실행용)

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
playwright install firefox
.\zap_setup.ps1
```

- `playwright install firefox`: XSS 실행 확인용 브라우저 설치
- `zap_setup.ps1`: ZAP 컨테이너 실행, 인증서(`zap_root_ca.cer`) 저장, ZAP 접속 정보(`config/zap_config.json`) 자동 생성
- 로그인이 필요한 대상이면 탐색용 Firefox에 프록시와 인증서를 설정해야 함
- 자세한 절차는 [실행 방법](docs/%EC%8B%A4%ED%96%89%EB%B0%A9%EB%B2%95.md) 참고

## 3. 사용법

```powershell
python src/web/app.py
```

- 브라우저에서 `http://127.0.0.1:1080` 접속 (로컬 접속만 허용)
- 설정 화면에서 타겟 URL을 저장한 뒤, 실행 화면에서 스캔 시작 (설정 파일은 저장 시 자동 생성)
- 진행 상황 확인, 스캔 중지, 지난 결과 조회, PDF 보고서 내려받기 제공
- 결과는 `results/collection_날짜_시각/` 폴더에 저장
- 화면별 사용법, 저장 파일 설명, 종료와 재실행은 [실행 방법](docs/%EC%8B%A4%ED%96%89%EB%B0%A9%EB%B2%95.md) 참고

## 4. 버그 및 디버그

### 디스크 용량이 부족할 때

- Docker가 쓰는 가상 디스크는 커지기만 하고 줄지 않으므로, 용량이 부족하면 `docker_compact.ps1`로 압축
- 관리자 권한 PowerShell에서 `.\docker_compact.ps1` 실행
- Docker와 WSL을 종료한 뒤 가상 디스크를 압축하고, 압축 전후 용량을 출력한 다음 Docker를 다시 시작
- 실행 중인 컨테이너(ZAP 등)가 끊기므로 스캔 중에는 실행하지 말 것

### 문제 확인 순서

1. 검사가 시작되지 않거나 수집 단계에서 멈춤
    - ZAP 컨테이너가 떠 있는지 확인 (`docker ps`)
    - `config/zap_config.json`의 포트·API 키가 실행 중인 ZAP 컨테이너의 값과 같은지 확인
    - 대상이 호스트에서 돌고 있다면 `target_url`이 컨테이너에서 접근 가능한 주소인지 확인 (예: `host.docker.internal`)
2. 결과가 "판단 보류"로 많이 나옴
    - 결과의 사유 코드를 확인. 사유 코드는 "왜 끝내지 못했는지"를 나타냄
    - 요청 전송 문제: `delivery_unknown`(POST 전송 실패로 서버 처리 여부 불명), `baseline_failed`, `attack_request_failed`
    - 브라우저 문제: `browser_timeout`, `browser_failed`
    - 저장형 XSS 재조회 문제: `revisit_url_missing`, `revisit_failed`, `sink_not_confirmed`
    - 기타: `discovery_failed`(사전 확인 실패), `prepare_failed`, `cancelled_by_user`, `not_reached`, `state_unclear`, `out_of_scope`
3. 터미널 출력 확인
    - 실행이 끝나면 `[RUN]` 접두어로 결과 파일 경로와 성공·실패 건수를 출력
4. 판정 단계별 상세
    - 각 결과 파일을 열어 해당 묶음의 응답과 사유를 직접 확인
    - 판정 기준은 위 "판정 기준 요약" 참고

## 5. 한계

- JSON, multipart 본문 파라미터는 아직 점검 대상으로 정리되지 않음
- DOM XSS의 브라우저 확인은 GET 요청만 지원
- 저장형 XSS는 폼(POST) 파라미터에만 적용
